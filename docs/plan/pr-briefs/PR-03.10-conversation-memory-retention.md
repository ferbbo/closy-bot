# PR Brief — PR-03.10 — Conversation Memory: short history + summary + retention

> Archivo: `docs/plan/pr-briefs/PR-03.10-conversation-memory-retention.md`
>
> Regla: 1 página. Machine-actionable. Sin scope extra.

## Objetivo

Mejorar continuidad conversacional “humana” guardando (a) historial corto acotado y (b) resumen+facts long-lived, con políticas de retención configurables y jobs de cleanup/sumarización para evitar crecimiento sin límite.

## Scope fence

### ✅ Included

- Modelo `MessageLog` (IN + OUT) con TTL (`expiresAt`) para historial corto.
- Campos de memoria en `Conversation`: `summary`, `memoryFacts`, `lastIntent`, `lastSummarizedAt`.
- Política de retención con defaults por env + override por merchant en `Merchant.playbookConfig`.
- Jobs con `@nestjs/schedule`:
  - cleanup: elimina `MessageLog` expirados y aplica cap por conversación.
  - summarization: actualiza `Conversation.summary` + `memoryFacts` periódicamente.
- Context builder para LLM:
  - últimos K logs + summary+facts + snapshot de estado de negocio (si existe).
- Observabilidad PII-safe (no loggear texto completo; enmascarar teléfono si aparece).

### ❌ Excluded

- Data warehouse / S3 archiving.
- Búsqueda avanzada tipo CRM / auditoría completa.
- Partitioning.
- Anonimización masiva de customers inactivos (phase 2, otro PR).

## Contratos / Interfaces

- Endpoints:
  - Sin endpoints nuevos.
- Persistencia (Prisma/models):
  - `MessageLog` (historial corto) y nuevos campos en `Conversation`.
- Retención:
  - Defaults por env y override por merchant:
    - `MESSAGE_HISTORY_DAYS` (default 30)
    - `MESSAGE_HISTORY_MAX_PER_CONVO` (default 50)
    - `LLM_CONTEXT_LAST_K` (default 10)
  - Override: `Merchant.playbookConfig.memory` (JSON) con keys opcionales:
    - `messageHistoryDays`, `messageHistoryMaxPerConvo`, `llmContextLastK`.
- Idempotencia:
  - Inbound: se mantiene dedupe por `InboundMessage.messageId` (ya existe).
  - MessageLog: `providerMessageId` se guarda para trazabilidad; no se usa como dedupe primario.

## Comportamiento

- Happy path:
  - Inbound webhook dedupea con `InboundMessage` y luego inserta `MessageLog` (direction=IN) con `expiresAt`.
  - Outbound (si existe outbox/worker o envío directo actual): inserta `MessageLog` (direction=OUT) al confirmar envío (ideal) o best-effort.
  - LLM recibe contexto: últimos K mensajes + summary+facts + estado de negocio disponible.
- Edge cases:
  - Duplicados inbound: no crear `MessageLog` extra (solo se crea si el inbound no fue duplicado).
  - Cleanup:
    - borra por `expiresAt < now()`.
    - safety cap: si una conversación tiene > `MESSAGE_HISTORY_MAX_PER_CONVO`, borrar los más antiguos incluso si no expiraron.
  - Sumarización:
    - no copiar chat completo; solo resumen 1–5 líneas y facts estables.
    - limitar longitud del `summary` (ej. 1000 chars) y truncar de forma segura.
  - Privacidad:
    - no persistir URLs de media; solo `mediaType`/metadatos mínimos.

## Riesgos y mitigaciones

- Crecimiento de DB por logs: TTL + cap + índices (`(conversationId, createdAt)`, `expiresAt`, `merchantId`).
- PII accidental en logs: no loggear texto en info; en debug siempre truncar/redactar.
- Costo LLM: K pequeño + summary compacto; no adjuntar historial completo.

## Notas

- Retention boundary MVP: 30 días (alineado con límite práctico de reply quoting de WhatsApp ≤ 30 días).
- Guardrails: LLM no inventa precio/stock/políticas/ETA (siempre desde backend).
- PII: preferir FK (`customerId`, `conversationId`) sobre repetir teléfonos; enmascarar si se loggea.
