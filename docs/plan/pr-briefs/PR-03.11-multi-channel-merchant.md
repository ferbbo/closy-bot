# Brief — PR-03.11 — Multi-channel per Merchant: Channel model + resolver + dynamic outbound

> **Status**: `APPROVED`
> **Archivo**: `docs/plan/pr-briefs/PR-03.11-multi-channel-merchant.md`
> **Regla**: Máx 2 páginas. Spec-locked. Sin scope extra.

## Objetivo

Permitir que cada Merchant tenga múltiples canales WhatsApp (y preparar Instagram en futuro) con resolución automática por `phone_number_id` y credenciales por canal, eliminando dependencia de env vars globales para multi-tenancy real.

## Scope fence

### ✅ Included

- Modelo `Channel` (Prisma): `type`, `externalId`, `merchantId`, `credentials`, `displayName`, `isActive`.
- Enum `ChannelType { WHATSAPP, INSTAGRAM }`.
- `ChannelRepository` con lookup por `(type, externalId)` y por `merchantId`.
- `MerchantResolverService.resolveByChannel(type, externalId)` → `{ merchant, channel }` (no `findFirst`).
- FKs: `Conversation.channelId`, `OutboxMessage.channelId` (nullable para backwards compat).
- `WhatsAppOutboundService.sendTextMessageWithCredentials(to, text, credentials)` para outbound dinámico.
- `OutboxDispatcher` usa credentials del channel (fallback a env vars si no hay channelId).
- Unknown channel handling: log structured warning + 200 OK (sin crash).
- Migración backwards-compatible: crea Channel desde Merchant + env vars existentes.
- Tests unit + e2e (multi-merchant multi-channel, channel desconocido).

### ❌ Excluded

- UI admin para CRUD de channels (puede ser PR aparte).
- Instagram OAuth flow completo (solo estructura preparada).
- Encrypt/decrypt helper real (placeholder, TODO comentado para futuro).
- Límites de channels por plan (puede ser PR aparte).
- Webhook separado para Instagram (fuera de alcance V1 MVP).

## Contratos / Interfaces

- Persistencia (Prisma/models):
  ```prisma
  enum ChannelType {
    WHATSAPP
    INSTAGRAM
  }

  model Channel {
    id           String      @id @default(cuid())
    merchantId   String      @map("merchant_id")
    type         ChannelType
    externalId   String      @map("external_id") // phone_number_id for WA
    displayName  String      @map("display_name")
    credentials  Json        // { accessToken, appSecret? }
    isActive     Boolean     @default(true) @map("is_active")
    createdAt    DateTime    @default(now()) @map("created_at")
    updatedAt    DateTime    @updatedAt @map("updated_at")

    merchant       Merchant        @relation(fields: [merchantId], references: [id])
    conversations  Conversation[]
    outboxMessages OutboxMessage[]

    @@unique([type, externalId])
    @@map("channels")
  }

  // FK en Conversation
  channelId String? @map("channel_id")
  channel   Channel? @relation(fields: [channelId], references: [id])

  // FK en OutboxMessage
  channelId String? @map("channel_id")
  channel   Channel? @relation(fields: [channelId], references: [id])
  ```

- ChannelRepository:
  ```typescript
  findByTypeAndExternalId(type: ChannelType, externalId: string): Promise<Channel | null>
  findByMerchantId(merchantId: string): Promise<Channel[]>
  findById(id: string): Promise<Channel | null>
  ```

- MerchantResolverService:
  ```typescript
  resolveByChannel(type: ChannelType, externalId: string): Promise<{ merchant: Merchant; channel: Channel } | null>
  ```

- WhatsAppOutboundService:
  ```typescript
  sendTextMessageWithCredentials(
    to: string,
    text: string,
    credentials: { accessToken: string; phoneNumberId: string }
  ): Promise<SendMessageResult>
  ```

- Idempotencia:
  - Key: `UNIQUE(type, externalId)` en `Channel` garantiza no duplicados.
  - Dedupe de mensajes inbound sigue siendo por `InboundMessage.messageId` (no cambia).

## Comportamiento

- Happy path:
  1. Webhook inbound llega con `phone_number_id` en metadata.
  2. `MerchantResolverService.resolveByChannel(WHATSAPP, phone_number_id)` retorna `{ merchant, channel }`.
  3. Orchestrator crea/actualiza Conversation con `channelId`.
  4. Orchestrator encola outbound con `channelId` en `OutboxMessage`.
  5. Dispatcher obtiene `Channel` del mensaje, extrae credentials, llama `sendTextMessageWithCredentials()`.
  6. WhatsApp Cloud API recibe request con `accessToken` y `phoneNumberId` del channel específico.

- Edge cases:
  - **Channel desconocido**: 
    - `resolveByChannel()` retorna `null` → controller log warning estructurado + return 200 OK (ACK a Meta).
    - No se crea conversation, no se procesa mensaje, no crash.
  - **OutboxMessage sin channelId** (backwards compat):
    - Dispatcher detecta `channelId === null` → usa `sendTextMessage()` legacy con env vars.
    - Permite rollout gradual sin romper mensajes encolados antes de la migración.
  - **Credentials inválidas**:
    - WhatsApp API retorna error → dispatcher marca mensaje como `FAILED` con retry backoff (comportamiento existente).

## Constraints

- **Guardrails**: No inventar channels ni credentials; siempre desde persistencia.
- **PII**: No loggear `accessToken` completo. Maskear `phoneNumberId` en logs.
- **Backwards compat**: Migración debe funcionar sin romper env var legacy.

## Riesgos y mitigaciones

| Riesgo                                                                                     | Mitigación                                                                      |
|--------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| Migración falla si no hay `WHATSAPP_PHONE_NUMBER_ID` en env                              | Migración crea Channel solo si env var existe; log warning si no.              |
| OutboxMessages encolados antes de migración no tienen `channelId`                         | Dispatcher detecta null y usa env vars legacy (fallback).                      |
| Credentials en JSON sin encriptar                                                          | Documentar TODO y agregar warning en logs; implementar encrypt en PR futuro.   |
| Channel desconocido recibe muchos webhooks y spamea logs                                  | Rate limit estructurado en logs (ej. log 1 vez por minuto por externalId).    |
