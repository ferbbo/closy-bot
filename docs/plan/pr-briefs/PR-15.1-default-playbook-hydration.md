# Brief — PR-15.1 — Default Playbook Hydration: Retail General + Backend-Driven Settings

> **Status**: `APPROVED`
> **Scope**: `MVP`
> **Archivo**: `docs/plan/pr-briefs/PR-15.1-default-playbook-hydration.md`

> **Regla**: Max 2 páginas. Spec-locked. Sin scope extra.

## Objetivo

Garantizar que todo merchant nuevo tenga `industry: 'retail_general'` y `playbookConfig` poblado desde creación (seed). El frontend dashboard elimina defaults hardcodeados y confía 100% en `GET /merchants/me` que SIEMPRE retorna `playbookConfig` no-null (hidrata con defaults cuando falta).

## Scope fence

### ✅ Included

- Migración Prisma: agregar `retail_general` al enum `Industry`
- Actualizar tipo TypeScript `Industry` en backend + frontend
- Actualizar `generic.config.ts` para usar `industry: 'retail_general'` explícitamente
- Seed playbook en creación de merchant (`auth.service.ts`)
- Hidratar `getProfile()` cuando `playbookConfig` es `null` (backward compat)
- Eliminar defaults hardcodeados del frontend (`DEFAULT_MESSAGES`, `DEFAULT_RULES`, `DEFAULT_LLM_PROMPT`, `getPlaybookOrDefaults()`)
- Tests unit + e2e backend
- Data migration opcional para merchants pre-existentes

### ❌ Excluded

- Selector UI de industria (MVP = Retail General único)
- Playbook editor visual avanzado
- Migración masiva automática en startup (es script manual/opcional)
- Feature flags (es MVP core, no B2)
- Cambios a los mensajes o FAQs del `GenericPlaybookDefaults` (ya están aprobados de PR-FE-OB-2)

## Comportamiento

### Happy path (merchant nuevo)

1. Usuario completa OAuth (Google/Microsoft)
2. `AuthService.handleCallback()` detecta nuevo merchant
3. Crea `Merchant` con `industry: 'retail_general'` y `playbookConfig: GenericPlaybookDefaults` (JSON)
4. Usuario accede a dashboard settings → `GET /merchants/me`
5. Backend retorna `playbookConfig` poblado → frontend renderiza campos pre-llenados
6. Usuario puede editar y guardar cambios

### Edge cases

**Merchant pre-existente con `playbookConfig: null`:**
1. `GET /merchants/me` → `MerchantSettingsService.getProfile()`
2. Detecta `playbookConfig === null`
3. Hidrata con `PlaybookService.getPlaybookForMerchant(merchant)` → defaults de `retail_general`
4. Retorna config hidratado (NO guarda en DB, solo retorna — save on demand)

**Merchant pre-existente con `industry: null`:**
1. `getProfile()` trata `industry: null` como `'retail_general'` (backward compat)
2. Hidrata playbook con `GenericPlaybookDefaults`

**Data migration opcional (script, no en runtime):**
- Script CLI `scripts/migrate-playbook-defaults.ts`:
  - Busca merchants con `industry: null` y/o `playbookConfig: null`
  - Actualiza: `industry: 'retail_general'`, `playbookConfig: GenericPlaybookDefaults`
  - Log: "Updated X merchants"

## Riesgos y mitigaciones

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|--------------|---------|------------|
| Migración enum falla en producción si hay valores `industry` corruptos | BAJA | ALTO | Validar enum values en pre-migration script (scan DB). Enum solo agrega valor, no modifica existentes. |
| Frontend rompe si backend aún no deployed (mismatch de tipos) | MEDIA | MEDIO | Deploy backend PRIMERO, luego frontend. Type `Industry` es union, agregar valor no rompe. |
| Merchant pre-existente con playbook partial (JSON incompleto) causa error al hidratar | BAJA | MEDIO | `PlaybookService.getPlaybookForMerchant()` hace merge (no replace), completa campos faltantes. Tests cubren esto. |
| Data migration script se ejecuta 2 veces → update innecesario (pero no destructivo) | BAJA | BAJO | Script es idempotente (SET where industry IS NULL). Doc indica: ejecutar 1 vez post-deploy. |

## Tech Notes

### Anti-patrones conocidos aplicados

1. **Prisma JSON cast:**
   ```ts
   playbookConfig: GenericPlaybookDefaults as unknown as Prisma.InputJsonValue
   ```
   - Doble cast obligatorio para JSON fields (anti-patrón TS2322).

2. **NestJS DTO properties:**
   - Si se crean DTOs nuevos, agregar `!` definite assertion a todas las props decoradas.

### Backward compat strategy

- `industry: null` → tratado como `'retail_general'` en `getProfile()`
- `playbookConfig: null` → hidratado con defaults en `getProfile()` (no guarda en DB hasta que merchant hace PATCH)
- Merchants pre-existentes no requieren re-login ni setup, funcionan de inmediato

### Data migration (opcional, no-bloqueante)

Script CLI para mass-update (ejecutar post-deploy si se desea):
```bash
# pseudocode
npx ts-node scripts/migrate-playbook-defaults.ts
# busca merchants con industry IS NULL or playbookConfig IS NULL
# UPDATE merchants SET industry='retail_general', playbookConfig={...} WHERE id IN (...)
```

No es bloqueante porque la hidratación en `getProfile()` cubre funcionalmente.
