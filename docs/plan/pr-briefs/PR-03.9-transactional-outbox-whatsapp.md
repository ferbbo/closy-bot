# PR Brief — PR-03.9 — Transactional Outbox: WhatsApp outbound confiable

> Archivo: `docs/plan/pr-briefs/PR-03.9-transactional-outbox-whatsapp.md`
>
> Regla: 1 página. Machine-actionable. Sin scope extra.

## Objetivo

Garantizar que si el backend confirma un commit en Postgres, el envío outbound a WhatsApp ocurra eventualmente (sin dual-write), desacoplando el webhook ACK del envío real.

## Scope fence

### ✅ Included

- Modelo/tabla `OutboxMessage` en Postgres (Prisma) para mensajes outbound WhatsApp.
- API interna `OutboxService.enqueueWhatsAppText(...)` usada por casos de uso/controladores.
- Worker dispatcher (Nest Schedule) que:
  - reclama filas con `FOR UPDATE SKIP LOCKED`
  - envía vía `WhatsAppOutboundService`
  - marca `SENT` o programa retry con backoff.
- Idempotencia best-effort:
  - `dedupeKey` estable + unique `(merchantId, dedupeKey)`.
- Logs PII-safe (teléfono enmascarado; texto truncado).
- Tests unitarios (enqueue + dispatcher success/failure + retry scheduling).
- Doc operativa `docs/plan/outbox.md`.

### ❌ Excluded

- Nuevos canales (IG/Messenger), templates avanzados, botones.
- Kafka/SQS/Redis/colas externas.
- CDC/Debezium.
- Garantía “exactly-once” real contra crash entre send y mark `SENT` (solo mitigación best-effort).

## Contratos / Interfaces

- Endpoints (si aplica):
  - Sin cambios a endpoints. El webhook debe seguir respondiendo 200 rápido.
- DTOs / payloads:
  - `enqueueWhatsAppText({ merchantId, to, text, replyToMessageId?, dedupeKey? })`
  - `payloadJson` persistido como `{ text: string; replyToMessageId?: string; metadata?: Record<string, unknown> }`.
- Persistencia (Prisma/models):
  - `OutboxMessage` con:
    - `status: PENDING | SENDING | SENT | FAILED`
    - `attempts`, `nextRetryAt`, `lockedAt`, `lockedBy`, `lastError`
    - `providerMessageId`, `sentAt`
- Idempotencia (si aplica):
  - Key: `dedupeKey` estable.
  - Constraint unique / estrategia: `@@unique([merchantId, dedupeKey])` y manejo de conflicto en enqueue (return existente).

## Comportamiento

- Happy path:
  - Inbound webhook persiste inbound + encola outbox en la misma transacción del caso de uso.
  - Worker reclama batch (SKIP LOCKED) → envía → marca `SENT`.
- Edge cases:
  - Duplicados:
    - `enqueue` con mismo `dedupeKey` no crea duplicado.
  - Reintentos:
    - error de red / 5xx → `FAILED`, incrementa `attempts`, calcula `nextRetryAt` con backoff exponencial (cap).
  - Out-of-order:
    - Se procesa por `createdAt ASC` best-effort; no hay garantía fuerte entre conversaciones.
  - Concurrencia:
    - múltiples instancias del worker no procesan la misma fila por `SKIP LOCKED`.

## Acceptance criteria (verificables)

- [ ] Migración crea `outbox_messages` y aplica con `pnpm db:migrate`.
- [ ] `WhatsAppController` no invoca envío directo en el camino normal; encola outbox.
- [ ] Worker procesa filas `PENDING/FAILED` con `nextRetryAt <= now()` usando `SKIP LOCKED`.
- [ ] Reintentos con backoff + `OUTBOX_MAX_ATTEMPTS`.
- [ ] Logs no imprimen teléfonos completos ni payload completo (texto truncado y teléfono enmascarado).
- [ ] Tests unitarios cubren: enqueue, success → SENT, failure → FAILED + retry.

## Comandos para validar

- `pnpm lint`
- `pnpm test`
- `pnpm db:migrate`

## Riesgos y mitigaciones

- Prisma no soporta `SKIP LOCKED` nativo → encapsular SQL raw en `OutboxRepository` y testear.
- Crash entre send y mark `SENT` → mitigación con `dedupeKey` + `providerMessageId` persistido (best-effort).
- Filas atascadas en `SENDING` → aplicar lock TTL (reclamar si `lockedAt` está vencido) o job de rescate.

## Anexo: Código a implementar

### A. Modelo Prisma (`prisma/schema.prisma`)

Agregar después del modelo `ProductVariant`:

```prisma
// ============================================================================
// PR-03.9: Transactional Outbox (Outbound WhatsApp)
// ============================================================================

enum OutboxChannel {
  WHATSAPP
}

enum OutboxMessageType {
  SEND_TEXT
}

enum OutboxMessageStatus {
  PENDING
  SENDING
  SENT
  FAILED
}

model OutboxMessage {
  id          String              @id @default(cuid())
  merchantId  String              @map("merchant_id")
  channel     OutboxChannel
  type        OutboxMessageType
  to          String
  payloadJson Json                @map("payload_json")
  dedupeKey   String?             @map("dedupe_key")

  status      OutboxMessageStatus @default(PENDING)
  attempts    Int                 @default(0)
  nextRetryAt DateTime            @default(now()) @map("next_retry_at")
  lockedAt    DateTime?           @map("locked_at")
  lockedBy    String?             @map("locked_by")
  lastError   String?             @map("last_error")

  providerMessageId String?       @map("provider_message_id")
  sentAt            DateTime?     @map("sent_at")
  createdAt         DateTime      @default(now()) @map("created_at")
  updatedAt         DateTime      @updatedAt @map("updated_at")

  merchant Merchant @relation(fields: [merchantId], references: [id])

  @@map("outbox_messages")
  @@index([merchantId])
  @@index([status, nextRetryAt])
  @@unique([merchantId, dedupeKey])
}
```

Agregar relación inversa en `Merchant`:
