# Brief — PR-05.1 — Merchant Commands: pipeline de operaciones WhatsApp

> **Status**: `APPROVED`
> **Archivo**: `docs/plan/pr-briefs/PR-05.1-merchant-commands-whatsapp.md`
> **Issue**: [#88](https://github.com/ferbbo/closy-bot/issues/88)
> **Regla**: Max 2 páginas. Spec-locked. Sin scope extra.

## Objetivo

Permitir que el merchant administre pedidos desde WhatsApp (confirmar, rechazar, marcar pagado, marcar enviado, ver pendientes), bifurcando el flujo del orchestrator para detectar mensajes del merchant vs. cliente, con comandos determinísticos y notificaciones al cliente en transiciones de estado.

## Scope fence

### ✅ Included

- Bifurcación en `ConversationOrchestrator`: detectar si mensaje viene del merchant (por `merchant.whatsappNumber`) → ruta admin
- Enum `ConversationType`: `CUSTOMER`, `MERCHANT_ADMIN` (Prisma)
- Campo `Conversation.type` (default: `CUSTOMER`) + migración
- Campo `Merchant.botPaused` (boolean, default `false`) + migración
- `MerchantCommandParser` service: parsear comandos textuales del merchant (case-insensitive, sin tildes)
- Comandos implementados:
  - `confirmar <orderCode>` → Order status `confirmed` + notifica cliente
  - `rechazar <orderCode> [motivo]` → Order status `cancelled` + notifica cliente con motivo
  - `pagado <orderCode>` → Order status `paid` + notifica cliente
  - `enviado <orderCode>` → Order status `shipped` + notifica cliente
  - `pedido <orderCode>` → muestra detalle del pedido al merchant
  - `pendientes` → lista pedidos `pending_payment` + `confirmed` del merchant
  - `hoy` → resumen del día (count pedidos, total COP)
  - `ayuda` → lista de comandos disponibles
  - `pausar bot` → `Merchant.botPaused = true` (mensajes de clientes NO procesados por bot)
  - `activar bot` → `Merchant.botPaused = false` (reactiva procesamiento)
- `MerchantCommandService`: ejecuta transiciones de estado validadas en Order
- Notificación al cliente (via `OutboxMessage`) cuando merchant cambia estado:
  - Confirmación: `"Tu pedido {orderCode} ha sido confirmado"`
  - Rechazo: `"Tu pedido {orderCode} fue rechazado: {motivo}"`
  - Pagado: `"Pago confirmado para tu pedido {orderCode}"`
  - Enviado: `"Tu pedido {orderCode} ha sido enviado"`
- Formato de respuestas al merchant: texto estructurado (no JSON)
- Tests unit (parser, service, validaciones) + e2e (flujo completo desde webhook)
- Actualización de `BACKEND-EXECUTION-GUIDE.md` con ejemplos cURL simulando merchant commands

### ❌ Excluded

- UI dashboard para pedidos (eso es PR-FE-06)
- Roles/permisos (multi-admin) — V1 solo 1 admin = merchant owner
- Message relay bidireccional (eso es PR-05.2)
- Confirmación interactiva (botones WhatsApp) — V1 solo comandos textuales
- Comandos para cancelar desde el cliente — futuro
- Notificaciones push a dashboard — futuro
- Plantillas de mensajes personalizables para notificaciones — V1 templates hardcoded

### Consumer Experience (API)

> **Nota**: Este PR NO agrega endpoints HTTP REST nuevos. La interacción es 100% vía WhatsApp:
>
> **Merchant → WhatsApp mensaje** → Webhook `/webhooks/whatsapp` → Orchestrator detecta merchant → `MerchantCommandParser` + `MerchantCommandService` → respuesta WhatsApp → OutboxMessage

**Ejemplo cURL simulando webhook (para testing):**
```bash
# Merchant envía "confirmar ORD-001"
# (El webhook Meta envía un payload con from = merchant.whatsappNumber)
curl -X POST http://localhost:3000/webhooks/whatsapp \
  -H 'Content-Type: application/json' \
  -d '{
    "entry": [{
      "changes": [{
        "value": {
          "metadata": { "phone_number_id": "1234567890" },
          "messages": [{
            "from": "+573009876543",  # merchant.whatsappNumber
            "id": "wamid.test-merchant-cmd-001",
            "timestamp": "1708560000",
            "type": "text",
            "text": { "body": "confirmar ORD-001" }
          }]
        }
      }]
    }]
  }'
```

**Respuesta esperada del bot al merchant (via OutboxMessage):**
```

Cliente Juan Pérez notificado.
```

## Comportamiento

### Happy path

1. Merchant envía mensaje "confirmar ORD-001" desde su WhatsApp (`merchant.whatsappNumber`)
2. Webhook recibido → `ConversationOrchestrator.process()`
3. Orchestrator detecta `input.from === merchant.whatsappNumber` → bifurca a ruta admin
4. `MerchantCommandParser.parse("confirmar ORD-001")` → `{ command: 'confirmar', args: { orderCode: 'ORD-001' } }`
5. `MerchantCommandService.confirmOrder(merchantId, 'ORD-001')`
   - Valida Order existe + pertenece al merchant + status actual permite transición
   - Update Order status `pending_payment` → `confirmed`
   - Enqueue `OutboxMessage` para notificar cliente: `"Tu pedido ORD-001 ha sido confirmado"`
6. Retorna respuesta al merchant: `"✅ Pedido ORD-001 confirmado\nCliente Juan Pérez notificado."`
7. OutboxDispatcher procesa notificación al cliente

### Edge cases

#### Duplicate command (idempotencia)
- Merchant envía "confirmar ORD-001" dos veces
- Segunda ejecución: Order ya está en status `confirmed`
- Response: `"ℹ️ Pedido ORD-001 ya está confirmado"`
- NO se envía notificación duplicada al cliente

#### Invalid transition
- Merchant envía "enviado ORD-002" pero Order está en status `cancelled`
- Response: `"❌ No se puede marcar como enviado un pedido cancelado"`
- Sin cambios en DB

#### Order not found
- Merchant envía "confirmar ORD-999"
- Response: `"❌ Pedido ORD-999 no encontrado"`

#### Ownership validation
- Merchant A intenta confirmar pedido de Merchant B (por error en bifurcación)
- Service valida `order.merchantId === merchantId`
- Response: `"❌ Pedido ORD-001 no encontrado"` (no exponer ownership)

#### Unknown command
- Merchant envía "inventario" (comando no implementado V1)
- Parser retorna `null`
- Response: `"❌ Comando no reconocido. Escribe 'ayuda' para ver comandos disponibles."`

#### botPaused active
- `Merchant.botPaused = true`
- Cliente envía "buscar zapatos"
- Orchestrator detecta `merchant.botPaused === true` → retorna early sin procesar
- Cliente NO recibe respuesta (mensajes acumulados en inbound)
- Merchant envía "activar bot" → `botPaused = false` → procesamiento reactiva

#### Merchant has no whatsappNumber
- `Merchant.whatsappNumber = null`
- Todos los mensajes procesados como cliente (no hay bifurcación posible)
- Funcionalidad merchant commands NO disponible para ese merchant

## Constraints

- Guardrails: validación de transiciones de estado (state machine simplificado, no formal FSM library V1)
- PII: logs solo usan `orderCode`, `merchantId`, `customerId` (no exponer nombres/teléfonos)
- Ownership: merchant solo puede operar pedidos propios (`order.merchantId === merchantId`)
- Timezone: para comando `hoy`, usar UTC (futuro: timezone por merchant en config)

## Riesgos y mitigaciones

| Riesgo | Impacto | Mitigación |
|--------|---------|------------|
| Merchant phone no registrado en DB → bifurcación no funciona | Alto | Validar en seed/onboarding que `merchant.whatsappNumber` existe. Documentar en BACKEND-EXECUTION-GUIDE. |
| Comandos ambiguos (ej: "confirmar" sin orderCode) | Medio | Parser retorna `null` si args incompletos. Merchant recibe "Comando mal formado". |
| Race condition: 2 comandos simultáneos sobre mismo Order | Bajo | Prisma transactions + optimistic locking (transición válida desde status actual). |
| Cliente aprende comandos merchant y los envía | Bajo | Bifurcación por phone match previene. Cliente con comandos → ruta normal (intent UNKNOWN). |
| `botPaused` bloquea permanentemente si merchant pierde acceso | Medio | Documentar: si merchant pierde phone, usar dashboard futuro (PR-FE-06) para reactivar. |
