## Objetivo

Implementar el flujo conversacional completo de búsqueda guiada → selección numerada → menú de opciones (agregar/detalles/cancelar) → confirmación + paginación, usando la capa `ExpectingService` ya disponible (PR-04.0).

## Scope fence

### ✅ Included

- Trigger **sin producto** (`sanitizedQuery === ""` tras limpiar el mensaje) → `ExpectingService.setExpecting(ask_search_query)` + responde `searchAskKeyword`. Aplica a cualquier keyword de `SEARCH_PRODUCT`: `"buscar"`, `"busco"`, `"tienes"`, `"hay"`, `"necesito"`, etc.
- Trigger **con producto** (`sanitizedQuery !== ""`) → búsqueda, lista paginada (máx 5/página), `setExpecting(select_product)`
- Paginación: keyword `"siguiente"` dentro de expecting `select_product` avanza a página siguiente
- Selección numérica (`"2"`) en expecting `select_product` → menú opciones + `setExpecting(product_options)`
- Menú opciones: 1 = Agregar al carrito (qty=1, `clearExpecting`), 2 = Ver detalles, 3 = Cancelar
- Ver detalles: muestra descripción/stock/precio + menú reducido (1=agregar/2=cancelar), `setExpecting(view_details)`
- Cancelar: `clearExpecting()` + mensaje `searchCancelled`
- Fallbacks: número OOB → `invalidProductSelection`; TTL expirado → `searchExpired`; input no numérico → re-prompt
- Agregar al carrito usa cantidad implícita = 1 (sin prompt)
- Keyword `"siguiente"` solo activo bajo expecting `select_product`
- Actualización `keyword-configs.ts`: `"siguiente"` como keyword de contexto bajo `SEARCH_PRODUCT`
- Tests unit + e2e para cada rama del flujo

### ❌ Excluded

- Selección de variantes (usa primera variante activa con stock)
- Prompt de cantidad al agregar (siempre qty=1)
- Botones interactivos WhatsApp (solo texto)
- Cart management (PR-04.2)
- Modificación/eliminación de carrito
- Integración con Checkout (PR-05)
- Cambios al `CheckoutService`

## Comportamiento

### Happy path (búsqueda → selección → agregar)

1. Usuario: `"buscar camiseta"` → lista ≤5 con footer de instrucciones
2. Usuario: `"2"` → menú opciones con nombre + precio
3. Usuario: `"1"` → confirmación con total de carrito

### Happy path (intent sin producto)

1. Usuario: `"buscar"` / `"busco"` / `"tienes"` / `"hay"` (sin nombre de producto) → `sanitizedQuery === ""` → bot pregunta qué buscar (`searchAskKeyword`)
2. Usuario escribe cualquier texto → se trata como query → lista de resultados normal

### Happy path (búsqueda → paginación)

1. `"buscar pantalones"` → 5 resultados + `nextHint` (hay más)
2. `"siguiente"` → página 2; si no hay más → `searchNoMorePages`

### Happy path (detalles → agregar)

1. `"2"` → menú opciones
2. `"2"` (detalles) → descripción/stock/precio + opciones 1/2
3. `"1"` → agregar al carrito + `clearExpecting()`

### Edge cases

- Número OOB (ej: `"6"` con 5 resultados) → `invalidProductSelection` sin cambiar estado
- Input no numérico (`"sí"`) en expecting `select_product` → `invalidProductSelection` sin cambiar estado
- TTL expirado → `searchExpired` + `clearExpecting()`
- Producto sin stock al agregar → `CartService.addItem()` retorna error → mensaje claro (behavior existente)
- Cualquier mensaje recibido en `ask_search_query` → se usa como query (no se re-clasifica intent)

## Constraints

- Guardrails: precio/stock siempre desde `CatalogService` (nunca del LLM).
- `ExpectingService` es la única fuente de verdad para estado multi-paso.
- Cantidad al agregar = 1 (simplificación UX WhatsApp MVP).
- Sin variantes complejas: primera variante activa con stock.
- **Fix de sincronización (keyword drift):** Agregar `'buscar'` al array `INTENT_KEYWORDS` en `search-catalog.flow.ts`. Actualmente `busco` está en ambas listas pero `buscar` solo está en `keyword-configs.ts`, por lo que `sanitizeQuery("buscar camiseta")` devuelve `"buscar camiseta"` en vez de `"camiseta"`. Fix de 1 línea, obligatorio para que REQ-01/REQ-02 funcionen correctamente.
- **Nota de deuda técnica:** La unificación de las dos listas de keywords (routing vs. sanitización) está diferida como `PR-REFACTOR-01` (P2, post-MVP).

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|--------|-----------|
| `expecting` race condition si dos mensajes llegan simultáneamente | `ExpectingService.setExpecting()` usa read-merge-write (atómico en Postgres); bajo riesgo en WhatsApp (1 thread por conv.) |
| Paginación cuando catálogo cambia entre páginas | `data.products` en expecting contiene snapshot; página 2 usa nueva búsqueda offset |
| Input ambiguo (`"sí"`) en `select_product` tratado incorrectamente | `parseNumericSelection` retorna null para no-numéricos → `invalidProductSelection` |
