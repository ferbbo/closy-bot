# Brief — PR-03.5.2 — Catálogo FTS: Full-Text Search español con tsvector

> **Status**: `AMENDED`

## Objetivo

Mejorar búsqueda de catálogo con PostgreSQL Full-Text Search (tsvector + ts_query) para lenguaje natural (Spanglish-friendly), sin romper búsqueda actual ILIKE. Habilita búsquedas como "algo para la cara" → productos skincare, "camiseta roja talla M" → matches correctos.

## Scope fence

### ✅ Included

- **Schema Product**: agregar campos `brand String?`, `tags String[]`, `imageUrls String[]` (SCR #78)
- Migración: columna `searchText` en `Product` + índice GIN con tsvector
- `ProductRepository.searchFts()`: método nuevo con raw SQL (`$queryRaw`)
- `CatalogService.searchProducts()`: delegación condicional por flag
- Feature flag `CATALOG_FTS_ENABLED` (default: `true`)
- Fallback automático: FTS retorna 0 → retry con ILIKE contains
- Middleware Prisma: regenerar `searchText` en create/update de productos
- Tests comparativos: FTS vs ILIKE, performance < 50ms con 500 productos
- Configuración `'simple'` (sin stemming) para soportar Spanglish (mix español/inglés)

### ❌ Excluded

- `pg_trgm` fuzzy matching / trigrams (diferente módulo PG)
- Sinónimos en DB o diccionarios custom
- Vector embeddings / semantic search
- FTS en FAQ/policies (diferente scope)
- UI/admin para administrar búsqueda
- Búsqueda multi-idioma (solo español por ahora)
- RAG o integraciones LLM en búsqueda

```typescript
  query: string;
  limit: number;
}

interface SearchFtsResult {
  id: string;
  name: string;

```

**Raw SQL structure (reference):**

| Componente | Implementación |
|------------|----------------|
| SELECT | `id, name, description, brand, category_id, merchant_id, tags, image_urls, is_active, created_at, updated_at, ts_rank(to_tsvector('simple', search_text), query) AS rank` |
| FROM | `products, plainto_tsquery('simple', $1) query` |
| WHERE | `merchant_id = $2 AND is_active = true AND to_tsvector('simple', search_text) @@ query` |
| ORDER BY | `rank DESC` |
| LIMIT | `$3` |

**Boost de peso:** Se puede implementar después del MVP con `setweight()` en migración (name → 'A', description → 'B'). Para V1 se usa orden simple por rank.

## Comportamiento

### Happy path

1. Request: `searchProducts(merchantId='m123', query='algo para la cara', limit=5)`
2. CatalogService lee flag `CATALOG_FTS_ENABLED=true`
3. Delega a `ProductRepository.searchFts(m123, 'algo para la cara', 5)`
4. Raw SQL ejecuta:
   ```sql
   SELECT *, ts_rank(...) AS rank
   FROM products
   WHERE merchant_id = 'm123'
     AND is_active = true
     AND to_tsvector('simple', search_text) @@ plainto_tsquery('simple', 'algo para la cara')
   ORDER BY rank DESC
   LIMIT 5
   ```
5. Retorna productos con "crema facial", "serum", "limpiador rostro" (words: `cara`, derivadas de description/tags)
6. Response incluye variants activas con stock > 0

### Fallback path (FTS retorna 0)

1. Request: `searchProducts(... query='producto inventado xyz')`
2. FTS ejecuta → 0 resultados
3. `searchFts()` detecta `results.length === 0`
4. **Retry automático** con ILIKE: `repo.search(merchantId, query, limit)` (implementación actual)
5. Si ILIKE también retorna 0 → array vacío (normal, producto no existe)
6. Log: `FTS returned 0, fallback to ILIKE succeeded with N results` (structured log)

### Feature flag OFF

1. Request: `searchProducts(... query='camisa roja')`
2. CatalogService lee flag `CATALOG_FTS_ENABLED=false`
3. **Directamente** delega a `repo.search()` (ILIKE contains, implementación actual PR-03)
4. No ejecuta FTS, no usa índice GIN
5. Retorna productos con ILIKE match
6. Performance posiblemente más lenta (sin índice), pero funcional

### Edge cases

- **Query vacío/null**: CatalogService valida antes de llamar repo (ya implementado en PR-03) → retorna []
- **Merchant sin productos**: FTS retorna 0 → fallback ILIKE retorna 0 → []
- **Producto sin description/tags**: `searchText` solo tiene `name + brand` → FTS sigue funcionando (partial match)
- **Tags vacío []**: `array_to_string(tags,' ')` → '' (string vacío, no rompe concatenación)
- **Query con caracteres especiales** (`@#$%`): `plainto_tsquery` los sanitiza automáticamente (safe)
- **Migración en producción con 1000+ productos**: `UPDATE` puede tomar tiempo → ejecutar en ventana de mantenimiento o con batches (Builder decide estrategia según volumen esperado MVP)

### E2E tests

- **Comparativa FTS vs ILIKE:**
  - Seed catálogo con 50 productos (mixto: ropa, belleza, mini)

  - Query `"camiseta azul"`:
    - FTS → retorna productos con description "color azul" + name "camiseta"
    - ILIKE → solo retorna si name contiene "camiseta" literal
- **Performance benchmark:**
  - Seed 500 productos
  - Ejecutar 10 búsquedas FTS consecutivas
  - Medir latencia promedio < 50ms

## Constraints

- **Guardrails**: No aplica (PR no modifica respuestas bot).
- **PII**: No aplica (productos son data pública del merchant).
- **Performance**: Índice GIN debe crearse para cumplir < 50ms. Sin índice, FTS puede ser más lento que ILIKE en catálogos pequeños.
- **Multi-tenancy**: `searchFts()` SIEMPRE filtra por `merchantId` (critical).
- **Backward compatibility**: Flag OFF → comportamiento idéntico a PR-03 actual.
- **Idioma**: Config `'simple'` (sin stemming) permite búsquedas con Spanglish común en LATAM ("makeup", "top", "blazer", "skincare").

## Riesgos y mitigaciones

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|--------------|---------|------------|
| Migración lenta con 1000+ productos (UPDATE genera `searchText`) | Media | Alto (downtime si blocking) | Ejecutar migración en ventana de mantenimiento o usar batches (`UPDATE ... WHERE id IN (SELECT ... LIMIT 1000)` iterativo) |
| FTS más lento que ILIKE en catálogos pequeños (< 50 productos) sin índice | Media | Bajo (solo afecta latencia) | Índice GIN mitiga. Documentar en README que FTS es óptimo para catálogos > 100 productos |
| Raw SQL `$queryRaw` con params inseguros (SQL injection) | Baja | Crítico | Usar **parameterized queries** (`$1, $2, $3`) SIEMPRE. Nunca interpolar strings. Test con query malicioso (`'; DROP TABLE--`) |
| Middleware Prisma no se ejecuta en operaciones bulk | Media | Medio (`searchText` desactualizado) | Documentar que bulk updates deben regenerar `searchText` manualmente. En MVP solo hay create/update uno a uno desde CSV import (que pasa por Prisma) |
| Sin stemming (`'simple'`), búsquedas infleccionales (`"camisetas"` vs `"camiseta"`) pueden fallar | Media | Bajo | Aceptable para MVP — Spanglish prevalece sobre stemming español perfecto. Futuro: considerar `unaccent` + custom dictionaries si necesario |
