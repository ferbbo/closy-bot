# Brief — PR-05.2 — Message Relay: merchant ↔ cliente vía bot

> **Status**: `APPROVED`
> **Archivo**: `docs/plan/pr-briefs/PR-05.2-message-relay.md`
> **Issue**: [#94](https://github.com/ferbbo/closy-bot/issues/94)
> **Regla**: Max 2 páginas. Spec-locked. Sin scope extra.

## Objetivo

Permitir que el merchant envíe mensajes directos a un cliente (y viceversa en modo handoff) vía el bot como intermediario, con relay bidireccional activable por comando desde WhatsApp.

## Scope fence

### ✅ Included

- Comando `msg <orderCode> <texto>`: merchant envía mensaje ad-hoc al cliente asociado al pedido
- Comando `handoff <orderCode>`: activa relay bidireccional (mensaje cliente → relay a merchant)
- Comando `cerrar handoff`: desactiva relay, bot retoma procesamiento normal
- Campo `Conversation.handoffActive` (boolean, default `false`) + migración
- Campo opcional `MessageLog.source` (string nullable) para marcar mensajes relayed + migración
- Formato mensaje a cliente: `"Mensaje de {merchantName}: {texto}"`
- Formato mensaje a merchant: `"Cliente {orderCode} dice: {texto}"`
- Relay usa `OutboxMessage` (misma infraestructura de PR-03.9)
- Bifurcación en orchestrator: si `handoffActive = true` → relay mensaje, NO procesar con flows/LLM
- Tests unit (parser + relay logic) + e2e (flujo completo)
- Actualización de `BACKEND-EXECUTION-GUIDE.md` con ejemplos

### ❌ Excluded

- Grupo WhatsApp nativo (V1 usa relay 1:1)
- Multi-admin (V1 solo 1 merchant owner)
- Relay de media (imagen/audio/video) — V1 solo texto
- UI inbox para gestión de relay — futuro dashboard PR-FE-08
- Notificaciones push a dashboard cuando hay relay activo — futuro
- Timeout automático de handoff activo — V1 requiere comando explícito `cerrar handoff`
- Estado `HANDOFF` formal en Conversation.status — V1 usa flag `handoffActive` solamente

## Contratos / Interfaces

### Persistencia (Prisma)

#### Conversation model (extensión)
| Field | Type | Constraints | Descripción |
|-------|------|-------------|-------------|
| `handoffActive` | Boolean | default: false | Si `true`, mensajes del cliente se relayean al merchant (NO procesados por flows/LLM) |

#### MessageLog model (extensión)
| Field | Type | Constraints | Descripción |
|-------|------|-------------|-------------|
| `source` | String | nullable | Marca origen de mensaje: `'relay'` para mensajes intermediados, `null` para mensajes normales |

#### MerchantCommandParser (extensión)

Nuevos comandos parseables:

| Comando | Pattern | Args parseados |
|---------|---------|----------------|
| `msg <orderCode> <text...>` | `msg ORD-001 Hola cliente` | `{ orderCode: 'ORD-001', text: 'Hola cliente' }` |

#### MessageRelayService (nuevo)

| Method | Input | Output | Descripción |
|--------|-------|--------|-------------|
| `sendMessageToCustomer` | `merchantId, orderId, text` | `Promise<void>` | Envía mensaje ad-hoc del merchant al cliente (OutboxMessage) |

| `formatMessageForMerchant` | `orderCode, text` | `string` | Formatea: `"Cliente {orderCode} dice: {text}"` |

### Consumer Experience (API)

> **Nota**: Este PR NO agrega endpoints HTTP REST. La interacción es 100% vía WhatsApp (webhooks):

**Merchant → WhatsApp mensaje** → Webhook `/webhooks/whatsapp` → Orchestrator detecta merchant → `MerchantCommandParser` → `MessageRelayService` → `OutboxMessage`

**Cliente → WhatsApp mensaje (con handoffActive = true)** → Webhook → Orchestrator detecta handoffActive → `MessageRelayService.sendMessageToMerchant()` → OutboxMessage al merchant

**Testability con cURL:**
- Se puede probar enviando webhooks inbound simulados (POST `/webhooks/whatsapp`)
- Auth: Webhook signature validation (mismo patrón PR-03.8)

### Idempotencia

- **Comando `msg`**: no requiere idempotencia (cada mensaje es único por contenido)
- **Comando `handoff`**: idempotente (setear `handoffActive = true` múltiples veces → mismo resultado)
- **Comando `cerrar handoff`**: idempotente (setear `handoffActive = false` múltiples veces → mismo resultado)
- **Relay mensajes**: cada mensaje tiene `providerMessageId` único (ya deduplicado por InboundMessage en PR-01)

## Comportamiento

### Happy path: comando `msg`

1. Merchant envía "msg ORD-001 Tu pedido sale mañana"
2. Webhook → Orchestrator → bifurcación merchant admin
3. Parser: `{ command: 'msg', args: { orderCode: 'ORD-001', text: 'Tu pedido sale mañana' } }`
4. `MessageRelayService.sendMessageToCustomer()`:
   - Query Order con `orderCode = 'ORD-001'` y `merchantId`
   - Obtener `customerId` de Order
   - Obtener `merchant.name`
   - Formatear: `"Mensaje de La Tienda de Maria: Tu pedido sale mañana"`
   - Enqueue OutboxMessage con `to = customer.phone`
   - Crear MessageLog con `direction = OUT`, `source = 'relay'`
5. Merchant recibe confirmación: `"✅ Mensaje enviado a cliente de ORD-001"`
6. Cliente recibe mensaje formateado por OutboxDispatcher

### Happy path: comando `handoff`

1. Merchant envía "handoff ORD-001"
2. Webhook → Orchestrator → bifurcación merchant admin
3. Parser: `{ command: 'handoff', args: { orderCode: 'ORD-001' } }`
4. `MessageRelayService.activateHandoff()`:
   - Query Order con `orderCode` + `merchantId`
   - Obtener `customerId` de Order
   - Query active Conversation (`customerId` + `merchantId` + `type = CUSTOMER`)
   - Update `Conversation.handoffActive = true`
5. Merchant recibe confirmación: `"✅ Handoff activo para ORD-001. Mensajes del cliente te llegarán directamente."`

### Happy path: relay bidireccional

1. **Condición previa**: `handoffActive = true` en Conversation
2. Cliente envía "Hola, ¿a qué hora pasan por mi casa?"
3. Webhook → Orchestrator → `processCustomerMessage()`
4. Orchestrator detecta `conversation.handoffActive === true`
5. **NO ejecuta flows/LLM** → en su lugar:
   - Query Order activo del cliente (last one with `customerId`)
   - `MessageRelayService.sendMessageToMerchant()`:
     - Formatear: `"Cliente ORD-001 dice: Hola, ¿a qué hora pasan por mi casa?"`
     - Enqueue OutboxMessage con `to = merchant.whatsappNumber`
     - Crear MessageLog con `direction = IN`, `source = 'relay'`
6. Merchant recibe mensaje formateado
7. Merchant responde con comando `msg ORD-001 Pasamos entre 2-4pm`
8. Cliente recibe respuesta formateada (ciclo `msg` normal)

### Happy path: cerrar handoff

1. Merchant envía "cerrar handoff"
2. Webhook → Orchestrator → bifurcación merchant admin
3. Parser: `{ command: 'cerrar_handoff', args: {} }`
4. `MessageRelayService.deactivateHandoff()`:
   - Query active Conversation del merchant donde `handoffActive = true`
   - Si encontrada: update `handoffActive = false`
   - Si no encontrada: retorna mensaje informativo
5. Merchant recibe confirmación: `"✅ Handoff cerrado. El bot retomará conversación con el cliente."`

### Edge cases

#### Order no encontrado (comando `msg`)
- Merchant envía "msg ORD-999 hola"
- Response: `"❌ Pedido ORD-999 no encontrado"`

#### Order no encontrado (comando `handoff`)
- Merchant envía "handoff ORD-999"
- Response: `"❌ Pedido ORD-999 no encontrado"`

#### Sin handoff activo (comando `cerrar handoff`)
- Merchant envía "cerrar handoff" sin handoff previo
- Response: `"ℹ️ No hay handoff activo en este momento"`

#### Cliente mensaje sin Order activo (relay)
- `handoffActive = true` pero cliente no tiene Order reciente
- Fallback: enviar al merchant sin `orderCode`: `"Cliente +573001234567 dice: {text}"`
- (Alternativa: desactivar relay automático y notificar merchant — decisión de implementación)

#### Merchant envía comando `msg` a sí mismo (error lógico)
- Validar que `customer.phone !== merchant.whatsappNumber`
- Response: `"❌ No puedes enviarte mensajes a ti mismo"`

#### Relay mensaje vacío
- Cliente envía mensaje vacío o solo whitespace con handoffActive
- NO relay, ignore mensaje

## Constraints

- Guardrails: el bot NO inventa respuestas cuando `handoffActive = true` (NO flows, NO LLM).
- PII: mensajes relayed contienen texto literal del cliente/merchant (ya minimizado en flows previos).
- Solo texto en V1: media relay (imagen/audio) es futuro.

## Riesgos y mitigaciones

| Riesgo | Impacto | Mitigación |
|--------|---------|-----------|
| Merchant olvida cerrar handoff → bot nunca retoma | MED | Documentar comando `cerrar handoff` en `ayuda`. Futuro: timeout automático (V2). |
| Cliente envía muchos mensajes en handoff → spam merchant | LOW | V1 sin rate limiting. Futuro: agrupar mensajes o agregar threshold. |
| Order sin Conversation activa (edge case) | LOW | Usar último Order del customer para obtener conversationId. Validar null. |
| Mensajes relayed sin contexto (cliente dice "si" sin pregunta) | LOW | Merchant puede ver historial previo con comando `pedido <orderCode>` (PR-05.1). |
