# PR Brief — PR-03.7 — Catalog Management API (Import + CRUD)

> Archivo: `docs/plan/pr-briefs/PR-03.7-catalog-management-api.md`
> 
> Regla: 1 página. Machine-actionable. Sin scope extra.

## Objetivo

Exponer endpoints HTTP para que un merchant pueda: (1) cargar/actualizar su catálogo mediante CSV bulk import con idempotencia por SKU, y (2) administrar productos/variantes con operaciones CRUD básicas, todo con multi-tenancy estricto y auth simple vía `apiKey`.

## Scope fence

### ✅ Included

- Módulo `CatalogManagementModule` + Controller HTTP
- Endpoint bulk import CSV reutilizando `ImportService.importFromCSV()`
- Endpoints CRUD básicos: `GET /products`, `GET /products/:id`, `POST /products`, `PATCH /products/:id`, `DELETE /products/:id` (soft delete)
- Auth Guard basado en `merchant.apiKey` (header `Authorization: Bearer <apiKey>` o `x-api-key: <apiKey>`)
- Validación con DTOs (class-validator) + whitelist/transform
- Scoping estricto: todos los endpoints solo devuelven/modifican resources del merchant autenticado
- Tests unitarios + e2e (happy path + multi-tenant isolation)
- Documentación: actualizar `.env.example` (sin cambios adicionales)

### ❌ Excluded

- UI/Admin dashboard (frontend es futuro)
- Integraciones POS/ERP/Shopify/WooCommerce (webhooks de terceros)
- Editor avanzado de catálogo (bulk edit UI)
- Versionado de cambios / auditoría (tracking de cambios históricos)
- Paginación tipo cursor avanzada (MVP: limit + offset simple o cursor básico)
- CSV complejo con comillas/escapes (usar parser simple existente)
- Recomendaciones basadas en ML

## Contratos / Interfaces

### Endpoints

#### 1. Bulk Import CSV
- **POST** `/api/catalog/import`
- Content-Type: `text/csv` o `multipart/form-data` (elegir uno MVP: preferir `text/csv` raw)
- Auth: required (merchant resolved via apiKey)
- Body: CSV content con formato `name,description,category,sku,price,stock`
- Response: 
  ```typescript
  {
    success: boolean;
    created: number;
    updated: number;
    errors: Array<{ row: number; field?: string; message: string; }>;
  }
  ```

#### 2. List Products
- **GET** `/api/products?q=<query>&category=<categoryName>&limit=20&cursor=<optional>`
- Auth: required
- Response:
  ```typescript
  {
    data: Array<ProductWithVariants>;
    total?: number; // optional
    cursor?: string; // optional for pagination
  }
  ```

#### 3. Get Product by ID
- **GET** `/api/products/:id`
- Auth: required
- Response: `ProductWithVariants` (includes variants array)
- Error: 404 if not found or if merchantId mismatch

#### 4. Create Product
- **POST** `/api/products`
- Auth: required
- Body (DTO):
  ```typescript
  {
    name: string;
    description?: string;
    categoryName: string; // resolve to categoryId internally
    variants: Array<{
      sku: string;
      price: number;
      stock: number;
      isActive?: boolean;
    }>;
  }
  ```
- Response: created `ProductWithVariants`

#### 5. Update Product
- **PATCH** `/api/products/:id`
- Auth: required
- Body: partial update (name, description, isActive)
- Response: updated `ProductWithVariants`
- Error: 404 if not found, 403 if merchantId mismatch

#### 6. Delete Product (soft)
- **DELETE** `/api/products/:id`
- Auth: required
- Effect: sets `isActive = false`
- Response: `{ success: true, id: string }`
- Error: 404 if not found, 403 if merchantId mismatch

### DTOs / Payloads

- **CreateProductDto**
  ```typescript
  class CreateProductDto {
    @IsString() @IsNotEmpty()
    name: string;
  
    @IsString() @IsOptional()
    description?: string;
  
    @IsString() @IsNotEmpty()
    categoryName: string;
  
    @ValidateNested({ each: true })
    @Type(() => CreateVariantDto)
    variants: CreateVariantDto[];
  }
  
  class CreateVariantDto {
    @IsString() @IsNotEmpty()
    sku: string;
  
    @IsNumber() @Min(0)
    price: number;
  
    @IsInt() @Min(0)
    stock: number;
  
    @IsBoolean() @IsOptional()
    isActive?: boolean = true;
  }
  ```

- **UpdateProductDto**: PartialType de CreateProductDto (sin variants, o con variants opcionales)

- **ProductListQueryDto**
  ```typescript
  class ProductListQueryDto {
    @IsString() @IsOptional()
    q?: string;
  
    @IsString() @IsOptional()
    category?: string;
  
    @IsInt() @Min(1) @Max(100) @IsOptional()
    limit?: number = 20;
  
    @IsString() @IsOptional()
    cursor?: string;
  }
  ```

- **ImportResponseDto**: retornar interface ImportResult ya existente

### Auth

- **Guard**: `ApiKeyAuthGuard`
  - Extrae `apiKey` de header `Authorization: Bearer <apiKey>` o `x-api-key: <apiKey>`
  - Busca `Merchant` por `apiKey` (campo unique)
  - Si no existe → 401 Unauthorized
  - Si existe → adjunta `merchant` a `request.merchant` (custom decorator `@Merchant()`)
- **Decorator**: `@Merchant()` (custom param decorator que extrae `request.merchant`)

### Persistencia (Prisma/models)

- **Sin cambios de schema** (reusar `Product`, `ProductVariant`, `Category`, `Merchant`)
- Métodos adicionales en `ProductRepository` (si no existen):
  - `findByIdAndMerchant(id: string, merchantId: string)` → asegurar aislamiento
  - `softDelete(id: string)` → `update({ isActive: false })`

### Idempotencia

- **Bulk Import (CSV)**: idempotencia via `sku` (upsert), ya implementado en `ImportService`
- **CRUD ops**: no requieren idempotency keys adicionales (operaciones stateless HTTP)

## Comportamiento

### Happy path

1. **Import CSV**:
   - Merchant hace POST con CSV → parser valida filas → upsert por SKU → retorna stats
2. **List products**:
   - Merchant hace GET con query → retorna productos scoped a merchantId
3. **Create/Update/Delete**:
   - Merchant envía request → Guard valida apiKey → operación scoped a merchantId → retorna resultado

### Edge cases

- **Duplicados**: Import CSV con mismo SKU → update (idempotente)
- **Cross-tenant access**: Request con apiKey de merchant A intenta acceder a producto de merchant B → 404 (no revelar existencia)
- **CSV con errores**: algunas filas fallan → retorna success=false + lista de errores con row/field/message
- **Invalid apiKey**: Guard retorna 401
- **Product not found**: 404
- **Payload grande (CSV)**: limitar tamaño en NestJS config (ej. 10MB max), procesar por batches internos (ya existe `BATCH_SIZE` en ImportService)

## Acceptance criteria (verificables)

- [ ] `POST /api/catalog/import` con CSV válido retorna stats correctas (created/updated/errors)
- [ ] Import CSV es idempotente: 2 cargas del mismo CSV con mismos SKUs no duplican productos
- [ ] `GET /api/products` solo retorna productos del merchant autenticado (no cross-tenant leaks)
- [ ] `POST /api/products` crea producto + variants correctamente scoped a merchant
- [ ] `PATCH /api/products/:id` rechaza con 404 si producto pertenece a otro merchant
- [ ] `DELETE /api/products/:id` hace soft delete (isActive=false) solo si pertenece a merchant
- [ ] Guard rechaza requests sin apiKey o con apiKey inválido (401)
- [ ] Tests e2e cubren happy path + multi-tenant isolation (al menos 2 merchants)
- [ ] `pnpm lint` y `pnpm test` y `pnpm test:e2e` pasan sin errores

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|--------|-----------|
| CSV parser simple (sin quotes/commas) no maneja casos complejos | Documentar limitación en README y en response de error. MVP asume CSV simple. |
| Payload grande de CSV (>10MB) puede saturar memoria | Configurar body size limit en NestJS (ej. 10MB). ImportService ya procesa por batches (BATCH_SIZE). |
| Cross-tenant leak si Guard falla | Tests e2e cubren multi-tenant isolation. Code review obligatorio. |
| apiKey en headers puede loggearse | No loguear headers raw; usar logger sin sensitive data. Documentar best practice (usar HTTPS). |

## Notas

- **Guardrails**: estos endpoints son de admin (merchant). El bot conversacional sigue extrayendo del CatalogService (no inventa precio/stock).
- **PII**: no hay PII en catálogo (solo datos de producto). No loguear apiKey en logs de aplicación.
- **Future work**: paginación avanzada (cursor real), webhooks de sync con POS/ERP, editor UI, auditoría de cambios (fuera de V1 MVP).
