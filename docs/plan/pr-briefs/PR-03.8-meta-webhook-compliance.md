# PR Brief — PR-03.8 — Meta WhatsApp Webhook Compliance

> Archivo: `docs/plan/pr-briefs/PR-03.8-meta-webhook-compliance.md`
> 
> Regla: 1 página. Machine-actionable. Sin scope extra.

## Objetivo

Hacer el backend NestJS compatible con el flujo real de Meta WhatsApp Cloud API webhooks: verificación GET, payload crudo POST, y validación de firma X-Hub-Signature-256.

## Scope fence

### ✅ Included

- GET `/webhooks/whatsapp` para verificación (hub.mode, hub.verify_token → hub.challenge)
- POST `/webhooks/whatsapp` acepta payload crudo de Meta (entry/changes/value/messages[])
- Mapper `whatsapp-webhook.mapper.ts`: payload Meta → InboundMessageDto normalizado
- Guard `MetaSignatureGuard`: valida X-Hub-Signature-256 con HMAC SHA-256 (timing-safe)
- `rawBody: true` en NestJS bootstrap
- Manejo de eventos `statuses` con early return (200 OK)
- Env vars: `WHATSAPP_WEBHOOK_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET`
- Actualización `.env.example` y `README.md`
- Tests E2E + unitarios

### ❌ Excluded

- Media download (solo logging por ahora)
- Templates/botones interactivos
- Cambios al orchestrator/LLM
- Cambios de DB (no hay migraciones)

## Contratos / Interfaces

### Endpoints

| Method | Route | Descripción |
|--------|-------|-------------|
| GET | `/webhooks/whatsapp` | Verification handshake Meta |
| POST | `/webhooks/whatsapp` | Recibir eventos crudos de Meta |

### Query params GET (verificación)

```typescript
interface WebhookVerifyQuery {
  'hub.mode': string;        // Debe ser "subscribe"
  'hub.verify_token': string; // Debe coincidir con WHATSAPP_WEBHOOK_VERIFY_TOKEN
  'hub.challenge': string;    // Retornar este valor como text/plain
}
```

### Payload POST (Meta crudo)

```typescript
interface MetaWebhookPayload {
  object: 'whatsapp_business_account';
  entry: Array<{
    id: string;
    changes: Array<{
      value: {
        messaging_product: 'whatsapp';
        metadata: {
          display_phone_number: string;
          phone_number_id: string;
        };
        contacts?: Array<{ profile: { name: string }; wa_id: string }>;
        messages?: Array<MetaMessage>;
        statuses?: Array<MetaStatus>;
      };
      field: 'messages';
    }>;
  }>;
}

interface MetaMessage {
  from: string;
  id: string;
  timestamp: string; // Unix epoch string
  type: 'text' | 'image' | 'document' | 'audio' | 'video' | 'sticker' | 'location' | 'contacts' | 'button' | 'interactive';
  text?: { body: string };
  image?: { id: string; mime_type: string; sha256: string };
  // ... otros tipos (ignorar por ahora, solo procesar text)
}

interface MetaStatus {
  id: string;
  status: 'sent' | 'delivered' | 'read' | 'failed';
  timestamp: string;
  recipient_id: string;
}
```

## Comportamiento

### Happy path

1. **GET verify**: Meta envía `hub.mode=subscribe`, `hub.verify_token=<token>`, `hub.challenge=xyz`
   - Si token coincide → responder `xyz` (text/plain, 200)
   - Si no → 403

2. **POST mensaje**: Meta envía payload con `messages[]`
   - Mapper extrae primer mensaje de tipo `text`
   - Llama pipeline existente (`WhatsAppService.processInboundMessage`)
   - Retorna 200 OK

3. **POST status**: Meta envía payload con `statuses[]` (sin `messages`)
   - Early return 200 OK sin procesar

### Edge cases

- **Múltiples mensajes en un payload**: procesar cada uno individualmente
- **Tipo no soportado (image, video, etc.)**: loggear warning, ignorar, retornar 200
- **Payload malformado**: validación defensiva, retornar 200 (Meta espera 200 siempre)
- **Firma inválida (con secret)**: rechazar con 401
- **Sin secret configurado**: log warning, permitir request (modo dev)

## Acceptance criteria (verificables)

- [ ] GET `/webhooks/whatsapp?hub.mode=subscribe&hub.verify_token=<valid>&hub.challenge=abc` → `abc` (200, text/plain)
- [ ] GET `/webhooks/whatsapp?hub.mode=subscribe&hub.verify_token=<invalid>&hub.challenge=abc` → 403
- [ ] POST `/webhooks/whatsapp` con payload Meta mensaje text → procesado, 200
- [ ] POST `/webhooks/whatsapp` con payload Meta `statuses` → 200 sin procesar
- [ ] POST con `X-Hub-Signature-256` inválida (secret configurado) → 401
- [ ] POST con `X-Hub-Signature-256` válida (secret configurado) → 200
- [ ] POST sin firma (secret NO configurado) → 200 + log warning

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|--------|------------|
| Breaking change en tests existentes que usan `/webhooks/whatsapp/inbound` | Mantener ambas rutas o actualizar tests |
| `rawBody` no disponible en NestJS < 10 | Documentar requisito NestJS >= 10.x |
| Secret filtrado en logs | No loggear secret; solo primeros 4 chars masked |
| Payload malformado de Meta rompe flujo | Validación defensiva + siempre retornar 200 |
| Timing attack en comparación de firma | Usar `crypto.timingSafeEqual` |
